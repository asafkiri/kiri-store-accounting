## צילום ומסמכים אחרי מעבר להקלדה ידנית

תוקן מסלול ״המשך בהקלדה ידנית״ מתוך הסורק: קבצים שנבחרו מועלים קודם דרך `documents`, ומזהי המסמכים עוברים לטופס ולחשבונית בשמירה מאושרת. אין קריאת AI במסלול הזה. כשל העלאה משאיר את התמונות בטיוטה ומאפשר ניסיון חוזר; מסמכים שכבר הועלו משמשים שוב. ברשימת החשבוניות מופיע מספר המסמכים, ובפתיחת חשבונית מופיע אזור ״תמונות ומסמכים מצורפים״ עם כפתורי פתיחה או הודעה שלא צורפו קבצים.

מיזוג ל־main אינו מפרסם את Firebase Hosting. יש להריץ את פקודת הפריסה בהמשך המסמך. בגרסת הסורק המעודכנת, צילום חדש פותח מסך עם ארבע פינות לגרירה, תצוגה מיושרת וכפתורי ״אשר״ / ״צלם שוב״ / ״ללא חיתוך״. הנוסח הישן ״כל העמוד נשמר ללא חיתוך״ מזהה ממשק שקדם לסורק. אין בתיקון שחזור אוטומטי של תמונות שלא צורפו לחשבוניות בעבר.

נוספו בדיקות לשמירה ידנית עם צילום ו־PDF, כשל העלאה וניסיון חוזר, שימוש חוזר אחרי כשל פתיחת הטופס, מניעת העלאה כפולה ופתיחת מסמך מחשבונית שמורה. בדיקות Chromium/WebKit עוברות מצילום שעובד ב־worker דרך הקלדה ידנית ועד שמירה מפורשת עם אותו מסמך, בלי AI.

## תוספת 2 — סעיפים 20–22

התוספת מתייחסת שוב לבסיס `3815da5`, אך נבדקה מול `main` של האפליקציה `7c1e2b5` והשרת `3b1df29`. סעיפי הרשימה המקורית כבר כלולים במיזוגים הקודמים; התוספת אינה מבטלת את התיקונים לעיל.

| סעיף | הטיפול |
|---|---|
| 20 | סגירה מהכפתור הראשי מאמצת טיוטה רק לתאריך היום בישראל. טיוטת יום אחר נשמרת בשם `saved-cash-<date>` ונפתחת טיוטה ריקה. פתיחת יום מההיסטוריה/טיוטות מכבדת את היום המבוקש ואת גרסתו. שינוי תאריך ברישום חדש מעדכן את מזהה הטיוטה בלי ליטול גרסה מיום קיים. |
| 21 | מוסכמה אחת באחסון: זיכוי הוא סכום שלילי. בעקבות תוספת 3 הטופס מקבל גובה סכום חיובי והסימן נגזר מסוג זיכוי אחרי Review; AI שומר את המספרים המודפסים ומסמן צורך בבדיקה. חשבונית 100 וזיכוי ‎-30 נותנים 70 ברשימות, במסך הספק ובדוחות. זיכויים ישנים עם סימן שגוי מסומנים, והסיכום שלהם אינו מוצג כמספר מטעה. אין שינוי אוטומטי ברשומות קיימות. |
| 22 | ״בטל את הניסיון״ משחרר את השדות גם בניתוק. לפני כתיבה נוספת נדרש אישור מהנתיב המוגן `POST /api/v1/mutations/:id/cancel`, שמכריע מול השמירה המקורית באמצעות אותו receipt בטרנזקציה. ניסיון שכבר נשמר מוחזר עם הרשומות הקשורות, בלי מחיקה או יצירה כפולה. מחיקת טיוטה לא פתורה שומרת רק ID ונתיב לבדיקה ברענון/בהגדרות, בלי השדות שנמחקו ובלי לפגוע בטיוטות אחרות. |

כיסוי התוספת: שחזור טיוטות ישנות עם version 0/2, שמירת היום הנכון, סיכומים עם זיכוי וסימון נתונים ישנים, שחרור אחרי 503 ואחרי ניתוק, reload, שמירה שהושלמה למרות כישלון התשובה, כשל אחסון מקומי, ומחיקת טיוטה תוך שמירת מזהה הבירור בלבד. בדיקות Chromium/WebKit כוללות סגירה ביום חדש וביטול/עריכה/מחיקה ללא חיבור. באמולטור נבדקת תחרות אמיתית בין שמירה וביטול על אותה קבלת Firestore. נתיב הביטול נבדק גם ללא token, עם token פסול ועם משתמש לא מורשה.

## אימות

בדיקות שחזור חדשות נכשלו מול ההתנהגות הקודמת ועוברות אחרי התיקון. בדיקות נלוות שומרות על בקשה ממתינה זהה, PDF ללא שינוי וגישת משתמש מורשה בלבד. עדכוני תיעוד נבדקו מול הקוד.

- אפליקציה: `npm test`, `npm run build`.
- דפדפנים: `npm run test:browser` ב-Chromium ו-WebKit. בחירת שמונה תמונות 5712×4284 שסכומן המקורי מעל 12 MiB, הקטנתן לפני ההעלאה, PDF ללא שינוי וגדלי טקסט/מגע בטלפון.
- שרת: `npm test`, `npm run build`, `node scripts/check-rules.mjs ../kiri-store-accounting`.
- Firebase emulators: תהליך אמיתי מול Admin/Auth/Firestore/Storage של פרויקט demo מקומי בלבד; כולל 403 עבור גישה ישירה עם token תקף.
- CI של השרת בונה גם Docker. הבדיקות אינן שולחות SMS אמיתי או קריאות AI בתשלום.

## הפצה ובדיקת הטלפון

יש למזג רק אחרי שהבדיקות עברו. push ל-main בריפו השרת מפעיל את Cloud Build הקיים. יש לוודא ב-Cloud Build שה-build של ה-commit הצליח וב-Cloud Run שה-revision החדש Ready ומקבל תעבורה. אין שינוי במשאבי השירות, CORS, allowlist או כללי Firestore/Storage.

פריסת הממשק דורשת חשבון Google מורשה. בתיקיית האפליקציה ב-Cloud Shell:

```sh
git pull --ff-only origin main &&
npm ci &&
npm test &&
npm run build &&
npx firebase-tools@14.16.0 deploy --project kiri-store-accounting --only hosting
```

לאחר Deploy complete רענן את האתר. בדוק הוספה אחרי עריכה נטושה, שמירה ורענון, ניסיון SMS נוסף אם נכשל, צילום אחד מהאייפון וסקירת הסכומים לפני שמירה. אישור הפריסה ובדיקת צילום אמיתי בטלפון נפרדים מהצלחה בבדיקות המבודדות.
